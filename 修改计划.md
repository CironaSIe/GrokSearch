## 1. reasoning_effort 改造

### 具体改法

`providers/grok.py` 的 `_build_search_payload` 中，将现在的：

```python
effort = _valid_reasoning_effort(reasoning_effort) or self.reasoning_effort
rp = _build_reasoning_prompt(effort)
# ... 中间若干行 ...
system_content = search_prompt
if rp:
    system_content += "\n\n" + rp
```

改为：

```python
effort = _valid_reasoning_effort(reasoning_effort) or self.reasoning_effort
# ... 中间行（direction/controls 不变）不变 ...
system_content = search_prompt

if effort:
    if self._use_responses_api:
        payload["reasoning"] = {"effort": effort}
    else:
        rp = _build_reasoning_prompt(effort)
        if rp:
            system_content += "\n\n" + rp

if dir_prompt:
    system_content += dir_prompt
```

`_build_reasoning_prompt` 函数保留不变。

### 副作用审查

| 风险 | 可能性 | 影响 | 对策 |
|------|--------|------|------|
| `xhigh` 不是 API 有效值（API 只认 `none/low/medium/high`） | 高 | API 可能拒绝或忽略 `xhigh` | `_valid_reasoning_effort` 中 `xhigh` 映射为 `high`（API 路径） |
| Responses API 路径少了 prompt 文本，模型行为细微差异 | 中 | 模型不再看到 "Be concise" / "Think step by step" 等文本指令 | 这是预期的——API 参数替代了文本指令，效果应该等价或更好 |
| `medium` 从无效（原 prompt hack 返回空字符串）变为有效（API 参数接受 `medium`） | 低—正 | medium 从"什么都不做"变成"适度推理" | 这是修复，不是副作用 |
| 非 Responses API 路径完全不受影响 | 无 | — | — |
| `_build_chat_payload` 不需要改（它没有 reasoning_effort 参数，且 fetch/describe 不涉及复杂推理） | 无 | — | 不修改 |

结论：安全。`xhigh` 映射到 `high` 是唯一需要处理的边界。

## 2. SourceExtractor + SourceRouter

### 具体改法

**新建目录 `src/grok_search/specialists/`**：

#### `specialists/__init__.py`

```python
from enum import StrEnum
from abc import ABC, abstractmethod

class SourceType(StrEnum):
    GITHUB_ISSUE = "github_issue"
    GITHUB_PULL = "github_pull"
    STACKEXCHANGE = "stackexchange"
    ARXIV = "arxiv"
    WIKIPEDIA = "wikipedia"
    GENERIC = "generic"

class SourceExtractor(ABC):
    @abstractmethod
    def match(self, url: str) -> bool:
        """同步 URL 匹配，不做网络请求"""
        ...

    @abstractmethod
    def kind(self) -> SourceType:
        ...

    @abstractmethod
    async def fetch_render(self, url: str, timeout: int) -> str | None:
        """返回结构化 Markdown，失败返回 None"""
        ...

class SourceRouter:
    def __init__(self, extractors: list[SourceExtractor]):
        self._extractors = extractors

    def resolve(self, url: str) -> tuple[str, SourceType] | None:
        """同步查找匹配的 extractor，返回 (content, type) 或 None"""
        for ex in self._extractors:
            if ex.match(url):
                return ex
        return None

NO_SPECIALIST_MATCH = object()
```

#### `specialists/wikipedia.py`

```python
class WikipediaExtractor(SourceExtractor):
    WIKI_PATTERN = re.compile(r"https?://([a-z]+)\.wikipedia\.org/wiki/(.+)")

    def match(self, url: str) -> bool:
        m = self.WIKI_PATTERN.match(url)
        self._lang = m.group(1) if m else ""
        self._title = m.group(2) if m else ""
        return bool(m)

    def kind(self) -> SourceType:
        return SourceType.WIKIPEDIA

    async def fetch_render(self, url: str, timeout: int) -> str | None:
        api_url = f"https://{self._lang}.wikipedia.org/api/rest_v1/page/summary/{self._title}"
        async with httpx.AsyncClient(timeout=timeout) as client:
            resp = await client.get(api_url, headers={"User-Agent": "GrokSearch/1.0"})
            if resp.status_code != 200:
                return None
            data = resp.json()
            return f"# {data.get('title', '')}\n\n{data.get('extract', '')}"
```

其他 specialist（GitHub, arXiv, StackExchange）结构类似，只换 API URL 和解析逻辑。

**修改 `server.py`**：全局构造 `SourceRouter` 实例，`web_fetch` 函数开始处加：

```python
# 在 Tavily 调用之前
url_obj = urlparse(url)
if url_obj.scheme in ("http", "https"):
    extractor = source_router.resolve(url)
    if extractor:
        try:
            content = await extractor.fetch_render(url, ft)
            if content:
                await log_info(ctx, f"Fetch Finished ({extractor.kind().value})!", config.debug_enabled)
                return content
        except Exception as e:
            await log_info(ctx, f"Specialist {extractor.kind().value} failed: {e}, falling through", config.debug_enabled)
```

### 副作用审查

| 风险 | 可能性 | 影响 | 对策 |
|------|--------|------|------|
| API key 泄漏（GitHub token 等） | 低 | token 可能被记录到日志 | 配置参数使用 `redact_sensitive_text` |
| specialist HTTP 超时阻塞主流程 | 中 | web_fetch 整体变慢 | specialist 走独立的超时控制（`ft`），异常捕获后静默降级 |
| specialist 内容质量不如 Tavily | 低 | 用户得到不够理想的结果 | 这是 edge case——specialist 用原生 API 应该比通用爬取结构更好 |
| specialist 匹配但源站变化导致 API 失效 | 中 | 匹配成功但内容获取失败 | 异常捕获后降级到 Tavily，日志记录便于排查更新 |
| URL 格式判断不严谨（如 `en.wikipedia.org` 误匹配） | 低 | 走向 specialist 但可能失败 | 正则收紧；失败自动降级 |
| GitHub 未配置 token 被限速 | 中 | specialist 限速失败后降级 | GitHub extractor 需要检查 token 是否配置，无 token 时可以直接跳过而非尝试后降级 |
| 跨模块依赖（specialists 引入 httpx/服务端特有逻辑） | 低 | 测试难度增加 | specialist 不依赖 server.py 的全局状态，只接收参数 |

结论：安全。异常处理链路保证了 specialist 失败不会阻塞下游 Tavily/Firecrawl。建议先只做 Wikipedia 和 GitHub，其余后面按需添加。

## 3. get_config_info 增强

### 具体改法

只在 `server.py` 的 `get_config_info` 函数内修改，不涉及其它文件：

1. 加 transport 字段
2. 加 Tavily/Firecrawl 可达性探测
3. 结构化输出

```python
async def get_config_info() -> str:
    import json
    import httpx
    import asyncio

    config_info = config.get_config_info()

    # Transport 探测
    transport = "responses" if (
        config.force_responses_api or "multi-agent" in config.grok_model.lower()
    ) else "chat_completions"

    # 并发探测三个后端
    async def probe_grok():
        try:
            api_url = config.grok_api_url
            api_key = config.grok_api_key
            async with httpx.AsyncClient(timeout=5.0) as client:
                start = time.time()
                resp = await client.get(
                    f"{api_url.rstrip('/')}/models",
                    headers={"Authorization": f"Bearer {api_key}"}
                )
                ms = (time.time() - start) * 1000
                return {
                    "reachable": resp.status_code == 200,
                    "response_time_ms": round(ms, 2),
                    "detail": f"HTTP {resp.status_code}" if resp.status_code != 200 else "ok",
                }
        except Exception as e:
            return {"reachable": False, "detail": str(e)}

    async def probe_tavily():
        if not config.tavily_api_key:
            return {"reachable": False, "detail": "skipped (not configured)"}
        # 复用已有 _call_tavily_extract 的测试
        result = await _call_tavily_extract("https://example.com", 10)
        return {"reachable": result is not None, "detail": "ok" if result else "failed probe"}

    async def probe_firecrawl():
        if not config.firecrawl_api_key:
            return {"reachable": False, "detail": "skipped (not configured)"}
        result = await _call_firecrawl_scrape("https://example.com", None, 10)
        return {"reachable": result is not None, "detail": "ok" if result else "failed probe"}

    grok_probe, tavily_probe, firecrawl_probe = await asyncio.gather(
        probe_grok(), probe_tavily(), probe_firecrawl()
    )

    # 模型列表（复用现有逻辑）
    models = config_info.get("connection_test", {}).get("available_models", [])

    return json.dumps({
        "transport": transport,
        "model": config.grok_model,
        "auth_mode": "api_key",
        "web_search_enabled": config.web_search_tool_enabled,
        "decon_pipeline_enabled": hasattr(config, 'decon_enabled') and config.decon_enabled,
        "grok": {"api_url": "...", **grok_probe},
        "tavily": {"api_url": config.tavily_api_url, **tavily_probe},
        "firecrawl": {"api_url": config.firecrawl_api_url, **firecrawl_probe},
        "available_models": models,
    }, ensure_ascii=False, indent=2)
```

### 副作用审查

| 风险 | 可能性 | 影响 | 对策 |
|------|--------|------|------|
| Tavily/Firecrawl probe 慢导致 get_config_info 超时 | 中 | 工具调用变慢 | 每个 probe 独立 5s 超时；`asyncio.gather` 并发执行，最慢 5s 返回 |
| `_call_tavily_extract` / `_call_firecrawl_scrape` 内部有日志或副作用 | 低 | 记录无意义的测试 URL 到日志 | 两个函数内部都有 `log_info`，但用测试 URL 是安全的 |
| `config_info` 中已有 `connection_test` 字段，重构后丢失 | 中 | 已有调用方依赖此字段 | 将 `connection_test` 作为兼容字段保留，不删除旧结构 |
| probe 过程中消耗 API 配额（Tavily/Firecrawl 按次计费） | 低 | 每次 get_config_info 消耗 1 次调用 | 可接受——这不是频繁调用的工具；如有顾虑可加结果缓存 |

结论：安全。核心变化是新增字段而非修改已有行为。`connection_test` 保留兼容字段避免破坏已有调用方。

## 4. 错误码枚举 — 不做

### 理由

MCP server 的消费者是 LLM，不是程序。LLM 读得懂 `"Grok 调用失败: HTTP 429 (Too Many Requests)"`。加 JSON-RPC error code 没有可衡量的收益。

### 副作用

无（不改）。
